# DREAM030526 — Design documentation product direction

**Date:** 3 May 2026  
**Status:** Active requirement set for report depth, export priority, and parity with office-style sample workbooks.

---

## 1. Purpose

The **authoritative design deliverable** for this product is **detailed, submission-grade design documentation**—not a Microsoft Excel file. The end user (bridge design office) must be able to **read, check, and file** a **Design Report** that tells the full technical story: **inputs, equation path, intermediate values, governing case, and acceptance statement**, in the same **line-by-line discipline** that traditional slab/bridge design works follow in **sample office Excel designs** and in **STRUDS-style** narrative reports.

Excel workbooks remain useful internally as a **structural model of how rows and formulas were sequenced in legacy projects**; they are **not** the primary handover to the client, the authority, or the peer checker.

---

## 2. What we do *not* require as a product output

- **We do not require the Excel (`.xlsx`) file** as a mandatory or promoted end-user download for design approval or submission.
- The team does **not** need to treat “download the 46/53-sheet workbook” as the main success path in the UI or in field workflow.
- Regeneration of `.xlsx` may continue to exist for **regression testing, golden-file checks, and optional “reference parity”** for engineers who still want a spreadsheet—**second class**, not the headline.

---

## 3. What we *do* require: detailed design reports

### 3.1 Definition

A **detailed design report** is a **single readable document** (HTML and/or PDF) that:

1. **Reproduces the technical intent** of the sample Excel-style designs **to the extent applicable** in this codebase—i.e. wherever the engine already computes a stable, deterministic row/column story (hydraulics, pier stability, abutment summaries, estimation, etc.).
2. Presents **explicit narrative lines**: **Design data** → **Step / itemised calculation** → **Numeric result** → **Clause or criterion** → **Hence O.K. / CHECK** (or equivalent verdict).
3. Avoids **abstract-only** prose that restates philosophy without numbers; every major block must remain **traceable to inputs and engine outputs** already used for drawings and BOQ.
4. Includes **workbook-faithful fragments** where implemented—e.g. **HYDRAULICS** rendered **row-by-row** in the same column order as the sheet model (A–H), not only a one-page summary table.

### 3.2 Line-by-line parity (scope statement)

**“Line by line to the extent applicable”** means:

| Area | Parity expectation |
|------|-------------------|
| Hydraulics | HTML/PDF must carry **full workbook-line grid** (or equivalent multi-row disclosure) matching the HYDRAULICS preview model, not only headline scalars. |
| Pier / abutment / stability | Narrative must include **sheet-level story** (load cases, forces, FOS, base pressure path) as generated for **STABILITY CHECK FOR PIER**, **TYPE1/C1** stability sheets—already wired via **full technical computation narrative** chunks. |
| Tech Report / verification | **Verification audit** lines must remain part of the trace, not replaced by marketing text. |
| Estimation | BOQ and cost trace must appear in narrative + summary tables where the engine supplies BOQ. |
| Sheets not yet mirrored row-by-row in HTML | Documented as **future extension**; do not claim full Excel clone until each sheet has a dedicated HTML/PDF fragment. |

### 3.3 Preferred export order (user workflow)

1. **HTML Design Report** — primary: fast iteration, print-to-PDF in browser, annexures.  
2. **Short PDF** — concise packaged report with full narrative blocks where implemented.  
3. **Comprehensive PDF** — extended calculation dossier (~200+ pages) when the office wants maximum paper depth.  
4. **DXF / SVG / validation** — supporting artefacts.  
5. **Excel workbook** — **optional / QA / legacy parity only**, not positioned as the main deliverable.

---

## 4. Engineering standards references (unchanged)

Reports remain aligned with **IRC SP 13** (hydraulics), **IRC:6** (loads), **IRC:112** (concrete), **IRC:78** (foundations), **IRC:5** where high-level clearance applies, and office practice for **stability FOS** (sliding, overturning, bearing) and **narrative traceability**.

## 6. Acceptance

This requirement set is **accepted** when:

- A reviewer can follow **from flood inputs to founding and stability** without opening Excel, using **HTML or PDF alone**, and  
- The UI **does not** present Excel as the default or necessary output for “design complete.”
